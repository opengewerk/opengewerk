# Das Fundament als eigene Pakete für weitere Anwendungen

## Kontext und Problemstellung

Mit OpenGewerk Haustechnik kommt eine weitere Anwendung in die Organisation: Software für Betreiber von Gebäuden und ihre Haustechnik, im eigenen Repository `opengewerk-haustechnik`. Sie führt andere Dinge als die Handwerkersoftware, nämlich Liegenschaft, Gebäude, Raum, Anlage, Pflicht und Nachweis statt Kunde, Auftrag und Beleg. Sie braucht aber dasselbe Fundament: Mandantentrennung über Row-Level Security, Anmeldung, Rechte, Abgleich ohne Netz, Audit-Log mit Hashkette, Regel-, Fristen- und Formular-Engine, Dateispeicher, PDF, Benachrichtigungen, Betrieb über Docker Compose. Der Kanzlei-Hub steht vor derselben Frage; sein Planungskonzept nennt denselben Stack, "damit Domänenpakete, Auth-Muster und Betriebsweise geteilt werden können".

Das Fundament ist heute kein eigenes Stück Code. Gemessen am 01.10.2026 auf `main`: rund 109.000 Zeilen in drei Paketen. Davon sind 31 Prozent Fundament ohne Fachbezug (199 Dateien), 21 Prozent Fundament, das Fachentitäten aufzählt oder Fachsymbole importiert (76 Dateien), 19 Prozent Fachentitäten, die beide Anwendungen brauchen könnten, und 28 Prozent reine Handwerker-Fachlichkeit. Von 63 Migrationen nennen 12 keine Fachtabelle. Am stärksten verflochten sind der Abgleich mit Zweigen je Entität, die Formular-Engine, die Stromkreise kennt, die Fristen-Engine, deren einzige Quelle das Angebot ist, und die Benachrichtigungen mit Beleg und Regiebericht als Anlässen.

Drei Beobachtungen bestimmen die Antwort:

- **Sicherheit liegt im Fundament.** Alle fünf bisher veröffentlichten Advisories betreffen es.
- **Abschriften laufen auseinander.** Die Prüfung "Schreibweise" ist in fünf Repositories "dieselbe" und trägt in einem davon seit dem 25.09.2026 drei Stämme mehr als in den anderen.
- **Die Dateien, die ein Schnitt umbauen muss, sind die meistgeänderten des Repositorys.** Ein Umbau neben laufender Arbeit an denselben Dateien wäre teuer. Die Entscheidung fällt zu einem Zeitpunkt, an dem die Arbeit an Phase 2 der Handwerkersoftware ruht und die Haustechnik Vorrang hat.

Daraus folgt die Frage: Wie bezieht eine weitere Anwendung das Fundament, ohne dass eine Sicherheitskorrektur an ihr vorbeigeht und ohne dass zwei Fassungen desselben Codes entstehen?

## Entscheidungstreiber

- Eine Sicherheitskorrektur im Fundament muss jede Anwendung erreichen, und es muss sich prüfen lassen, ob sie angekommen ist.
- Es gibt genau eine Fassung des Fundaments. Keine Anwendung hält eine eigene.
- Anwendungen verschiedener Betreiber veröffentlichen unabhängig (ADR 0001).
- Was fachlich ist, darf das Fundament nicht kennen: weder Kunde noch Beleg, weder Liegenschaft noch Pflicht.
- Eine gemergte Migration wird nicht angefasst, und laufende Instanzen kennen ihre Hashes.
- Eine Änderung am Fundament muss sich in der einbindenden Anwendung prüfen lassen, bevor irgendetwas veröffentlicht wird.

## Betrachtete Optionen

Für den Schnitt:

1. **Abschrift**: das Fundament einmal kopieren, danach pflegt jede Anwendung ihre Fassung.
2. **Übernahme mit Herkunftsnachweis**: Kopie von einem benannten Commit, jede übernommene Datei bleibt über eine Herkunftsdatei und eine Prüfung in der CI an ihre Quelle gebunden, die verflochtenen Dateien werden in der Kopie angepasst.
3. **Ein Monorepo**: die Haustechnik als weitere Anwendung im Repository `opengewerk`.
4. **Eigene Pakete im Hauptrepository**: das Fundament wird unter `packages/platform/` herausgelöst, jede weitere Anwendung bindet einen festen Stand davon ein.
5. **Ein eigenes Repository für das Fundament.**

Für die Einbindung der Pakete in eine Anwendung mit eigenem Repository:

- A. **Git-Submodul**, die Pakete werden im Arbeitsbereich der Anwendung mitgebaut.
- B. **Archiv am Release**, die Anwendung nennt eine Fassung.
- C. **Registry** (npm oder GitHub Packages).
- D. **Git-Abhängigkeit** des Paketmanagers auf ein Unterverzeichnis.

## Entscheidung

Gewählt wurden **Option 4**, eigene Pakete im Hauptrepository, und für die Einbindung **A**, das Git-Submodul.

**Die Pakete**

1. Das Fundament liegt unter `packages/platform/` in drei Paketen, entlang derselben Grenze wie die Anwendung. Die Paketliste aus ADR 0009 wird damit ergänzt:

   ```
   opengewerk/
     packages/
       platform/
         domain/        # Fundament ohne I/O: Mandant, Zugehörigkeit, Rechte, Abgleich, Regel-, Fristen- und Formular-Engine
         server/        # Datenbankzugriff, Migrationslauf, Anmeldung, Guard, Audit-Log, Dateispeicher, Renderer, Versand
         web/           # Abgleich-Client, Sitzung, Tor, Bausteine, Tokens, Hülle
       domain/          # Fachlichkeit der Handwerkersoftware
       server/
       web/
       gewerke/<name>/  # wie bisher (ADR 0008)
   ```

   Die Pakete heißen `@opengewerk/platform-domain`, `@opengewerk/platform-server` und `@opengewerk/platform-web`.

2. **Die Richtung der Abhängigkeit ist eine Eigenschaft des Paketgraphen.** Ein Paket des Fundaments hängt von keinem Paket einer Anwendung ab. Ein Import in die falsche Richtung scheitert deshalb als fehlendes Modul, und eine Lint-Regel sagt dazu, welche Regel das ist. Ein Test liest die `package.json` der drei Pakete und wird rot, wenn dort eine Abhängigkeit auf ein Anwendungspaket auftaucht.

3. **Was fachlich ist, kommt über Register.** Das Fundament kennt den Mechanismus, die Anwendung die Liste: welche Entitäten abgleichen und nach welchen Regeln, welche Rechte es gibt, welche Rollen, wie eine Tabelle im Änderungsprotokoll heißt, welche Nummernkreise und Einstellungen es gibt, woraus Fristen entstehen, welche Formulare ein Paket mitbringt, welche Anlässe benachrichtigen, was in der Navigation steht. Rollen führt das Fundament als Daten und nicht als feste Liste; damit ist der Schritt aus dem Nachtrag vom 24.09.2026 in ADR 0008 vorgezogen, der dort für das zweite Gewerk vorgesehen war.

4. **Herausgelöst wird in Raten**, in der Reihenfolge, in der die Haustechnik etwas braucht: zuerst, was keine Fachlichkeit kennt, danach ein verflochtener Teil nach dem anderen, sobald seine Naht gebaut ist. `@opengewerk/domain` exportiert weiter alles, was es bisher exportiert hat, damit die Importe der Handwerkersoftware nicht in einem Zug umziehen müssen. Was noch nicht herausgelöst ist, bleibt, wo es ist; eine Abschrift entsteht in keinem Schritt.

**Die Einbindung**

5. Eine Anwendung mit eigenem Repository bindet `opengewerk` als Git-Submodul unter `upstream/opengewerk` ein, auf einen festen Commit. Die Verzeichnisse `upstream/opengewerk/packages/platform/*` sind Mitglieder ihres pnpm-Arbeitsbereichs: ihre Abhängigkeiten stehen in der Lockdatei der Anwendung, und Turborepo baut sie vor den Paketen, die sie brauchen. Es wird nichts veröffentlicht, es braucht kein Konto und keinen Schlüssel.

6. **Gegengeprüft am 01.10.2026** mit pnpm 12.4.2, Turborepo 2.10.13 und TypeScript 7.0.2: pnpm führt ein Paket aus dem Submodul als Mitglied des Arbeitsbereichs, die Lockdatei bekommt dafür einen eigenen Eintrag, Turborepo baut es zuerst, und das Ergebnis läuft. Die Datei `pnpm-workspace.yaml` im Submodul stört nicht, weil pnpm die des Verzeichnisses nimmt, in dem es gestartet wird.

7. **Angehoben wird der Stand mit einem Pull Request** in der Anwendung, der den Commit des Submoduls und die Lockdatei bewegt. Dependabot schlägt ihn wöchentlich vor. Die CI der Anwendung prüft sie dabei gegen den neuen Stand.

8. Die einbindende Anwendung übersetzt die Pakete mit ihrem eigenen Werkzeug. Sie hält deshalb dieselben Reihen wie ADR 0009: Node, pnpm, TypeScript.

**Was daneben gilt**

9. **Jede Anwendung hat ihren eigenen Migrationsstrom.** Die Handwerkersoftware behält ihre Migrationen unverändert. Das Fundament liefert die Schema-Module und die SQL-Bausteine für Rollen, Policies, Funktionen und Trigger; eine neue Anwendung beginnt mit einer Ausgangsmigration, die daraus entsteht. Die Spalten von `audit_entries` und der Fingerabdruck der Hashkette sind in jeder Anwendung dieselben; der Test, der die Spalten festhält, gehört zum Fundament.

10. **Zwei Anwendungen laufen nebeneinander**, jede mit eigenem Compose-Projekt, eigenem PostgreSQL-Container, eigenem Port und eigenem Hostnamen. Die Datenbankrollen heißen in beiden gleich; das störte nur in einem gemeinsamen Cluster, und den gibt es nicht. Was ein Mensch sieht oder was nach außen einen Namen trägt (Produktname, Abbild, Compose-Projekt, Port), nennt die Anwendung und nicht das Fundament.

11. **Eine Sicherheitskorrektur im Fundament** erscheint wie bisher als Fassung der Handwerkersoftware. Jede einbindende Anwendung hebt danach ihren Stand an und veröffentlicht ihrerseits. Das Advisory nennt alle betroffenen Anwendungen, und die `SECURITY.md` der Organisation beschreibt den Weg.

### Konsequenzen

Gut:

- Es gibt eine Fassung des Fundaments. Eine Korrektur dort kommt in jeder Anwendung an, sobald sie ihren Stand anhebt, und am Commit des Submoduls lässt sich ablesen, ob das geschehen ist.
- Die Nähte, die die Haustechnik braucht, sind dieselben, die das zweite Gewerk und der Kanzlei-Hub brauchen. Sie entstehen einmal.
- ADR 0001 bleibt, wie es ist: jede Anwendung hat ihr Repository, ihre Fassung und ihre Betreiber.
- Eine Änderung am Fundament lässt sich in der Haustechnik prüfen, bevor sie gemergt ist: der Arbeitsbaum des Submoduls ist ein gewöhnlicher Klon.

Schlecht:

- Der Umbau fasst die meistgeänderten Dateien an. Solange er läuft, ist parallele Arbeit an der Handwerkersoftware teurer als sonst.
- Eine Änderung am Fundament, die die Haustechnik braucht, hat zwei Schritte in fester Reihenfolge: erst hier mergen, dann dort den Stand anheben. Das ist das Schlechte aus ADR 0001, hier für das Fundament.
- Ein Submodul ist unbequem. Wer klont, braucht `--recurse-submodules`; wer aus dem Quelltext installiert, braucht den Schritt in `start.sh`. Ein Release-Paket braucht ihn nicht, es zieht fertige Abbilder.
- Die Tests des Fundaments benutzen heute Kunden, Objekte und Belege als Material und bleiben deshalb zunächst bei der Handwerkersoftware. Bis sie neutrales Material haben und mit umziehen, prüft die CI der Haustechnik das Fundament nur mittelbar.
- Die Nähte entstehen aus zunächst zwei Verbrauchern. Ein dritter kann zeigen, dass eine davon falsch geschnitten ist.

Nachträge:

- **Nachtrag vom 01.10.2026, woraus eine Ausgangsmigration entsteht.** Punkt 9 ist umgesetzt (`opengewerk-haustechnik#6`). Die Tabellen des Fundaments, also Mandanten, Konten und Sitzungen, Zugehörigkeiten und Einladungen, Audit-Log und Abgleich, liegen als Schema-Module in `platform-server` und kommen über den Einstieg `@opengewerk/platform-server/schema`; die Handwerkersoftware reicht sie aus ihrer Schema-Datei weiter. Was `drizzle-kit` nicht schreibt, liegt als SQL-Dateien unter `packages/platform/server/sql/`: die Rolle der Anwendung und die Funktionen und Trigger des Audit-Logs, des Abgleichs und der Ersteinrichtung. Was eine Tabelle darüber hinaus braucht, `FORCE`, die Rechte der Anwendungsrolle und die zwei Trigger, steht als eine Beschreibung je Tabelle im Code. Eine neue Anwendung lässt `drizzle-kit generate` ihre erste Migration schreiben und `completeInitialMigrationIn` die Bausteine darum setzen, samt Rücknahme; danach ist die Datei eingefroren wie jede Migration. **Maßgeblich sind die Migrationen der Handwerkersoftware und nicht die Bausteine:** jede Migration ist auf einer Installation gelaufen, ein Baustein nicht. Ein Test dort baut deshalb eine Datenbank aus den Bausteinen allein und eine aus allen Migrationen und vergleicht am Katalog, was PostgreSQL über Spalten, Schlüssel, Policies, Rechte, Trigger, Enums und Funktionen sagt, bis zu der Frage, wer eine Funktion aufrufen darf. An einer Tabelle des Fundaments gilt der Vergleich in beide Richtungen, damit ein Trigger, den die Bausteine vergessen haben, von einem zu unterscheiden ist, den die Anwendung angehängt hat: den eigenen nennt die Anwendung. Die Rollen einer Zugehörigkeit sind im Fundament Zeichenketten, denn welche Rollen es gibt, ist die Liste der Anwendung. Die Katalogfragen zur Mandantentrennung, die bisher nur in den Tests der Handwerkersoftware standen, gehören seitdem zu `@opengewerk/platform-server/testing` und laufen im Fundament über einer Datenbank, die nichts als das Fundament trägt. Soweit es die Datenbank betrifft, prüft die CI einer einbindenden Anwendung das Fundament damit nicht mehr nur mittelbar.
- **Nachtrag vom 02.10.2026, die Anmeldung und was eine Anwendung dazu sagt.** Der Guard, die Identität einer Anfrage, die Herkunftsprüfung und die Anmeldung selbst liegen in `platform-server` (`opengewerk-haustechnik#7`). Vier Dinge sind dabei entschieden, die Punkt 3 und Punkt 10 nur andeuten. **Erstens die Wörter:** das Fundament schreibt seine Sätze einmal, für jede Anwendung, und nennt darin keinen Mandanten und keine Rolle beim Namen. Wo ein Satz das muss, weil er sagt, wo jemand nachfragen soll oder wer eine Sperre aufhebt, bringt ihn die Anwendung mit, als ganzen Satz und nicht als Wort zum Einsetzen: ein Mandant heißt in der Handwerkersoftware "Betrieb" und in der Haustechnik "Betreiber", und ein eingesetztes Wort stimmt im Deutschen in keinem zweiten Fall. **Zweitens die Rollen:** bis sie mit dem Katalog der Rechte zu Zeilen eines Mandanten werden, nennt die Anwendung ihre Liste, die Rolle, die einen Mandanten führt und die das erste Konto bekommt, und die Frage, welche Rollen einen zweiten Faktor brauchen (`AccessRules`). Das kommt als Argument an jede Funktion, die es braucht, und unter einem Token an die Controller; ein Register, in das sich eine Anwendung einträgt, gibt es nicht. **Drittens better-auth:** was der Rest eines Servers von der Anmeldung fragt, steht als eigene Schnittstelle im Fundament, vier Dinge, und nicht als der Typ, den better-auth zurückgibt. Der trägt jede Route jedes Plugins in sich und lässt sich in keiner Deklarationsdatei eines Pakets benennen; nebenbei greift so keine Anwendung an dem vorbei, was dort steht. **Viertens die Mails:** ein Konto gehört zur Instanz und jeder Mailserver zu einem Mandanten, also entscheidet die Anwendung, worüber eine Nachricht geht. Das Fundament kennt nur die zwei Anlässe, den Link zu einem neuen Passwort und den Hinweis auf einen neuen Passkey, als Funktionen, die es aufruft. Die Tests der Anmeldung laufen seitdem im Fundament selbst, mit einer Anwendung, die niemandem gehört ("Probewerk": zwei Rollen, zwei Rechte, ein Controller), und ein Test hält fest, dass im Paket weder der Name einer Anwendung noch eine ihrer Rollen als Literal steht. Der Satz unter "Schlecht", die Tests des Fundaments blieben zunächst bei der Handwerkersoftware, gilt damit für die Anmeldung nicht mehr; bei ihr bleibt, was ihre Kunden, ihre Mails und den Bereich der Instanz braucht. Die Verwaltung der Zugänge im Büro folgt mit einem eigenen Schritt, weil ihr Controller Rechte nennt und Einladungen per E-Mail verschickt.
- **Nachtrag vom 02.10.2026, die Verwaltung der Zugänge.** Wer in einem Mandanten arbeitet, liegt seit demselben Tag ebenfalls in `platform-server`, und `opengewerk-haustechnik#7` ist damit abgeschlossen: die Liste der Leute, die Einladung, die Rollen, das Sperren, die Geräte einer Person und die Regel, dass ein Mandant die letzte Person, die ihn führt, nicht verliert. Drei Dinge sind dabei dazugekommen. **Die zwei Rechte der Routen nennt das Fundament selbst**, `membership.read` und `membership.write`: die Routen gehören ihm, also auch die Namen, nach denen sie fragen. Eine Anwendung führt beide in ihrem Katalog und entscheidet, welche ihrer Rollen sie hält; wer Rollen vergibt, kann sich die führende geben, also gehören sie zu ihr und zu keiner anderen. Bei der Handwerkersoftware hält eine Zeile schon beim Übersetzen fest, dass ihr Katalog beide kennt. Zieht der Katalog der Rechte selbst ins Fundament, gehören diese zwei zu dem Teil, den es mitbringt. **Die Einladung per E-Mail ist eine Naht mit drei Fragen:** ob dieser Mandant verschicken kann, gefragt, bevor die Einladung geschrieben ist; die Übergabe der fertigen Einladung, deren Token erst entsteht, wenn die Nachricht hinausgeht; und wie die Nachricht steht. Mailserver je Mandant, Postausgang und Wortlaut bleiben bei der Anwendung, bis die Benachrichtigungen selbst umziehen. Eine Anwendung ohne diese Naht gibt Links aus, und der Wunsch nach einer Mail wird mit einem Satz abgelehnt. **Die Leute eines Mandanten nach Namen** (`listColleagues`), aus denen eine Anwendung auswählt, wem sie etwas gibt, gehören dazu: es sind dieselben zwei Lesevorgänge wie in der Verwaltung, erst die Zugehörigkeiten im Mandanten und dann die Konten zu genau diesen Kennungen, und eine zweite Fassung daneben wäre eine zweite Stelle, an der die Trennung der Mandanten gehalten werden muss. Die Anwendung der Tests hat eine dritte Rolle bekommen, damit ein Wechsel der Rolle an einer Route messbar ist, ohne dass ein zweiter Faktor dazwischentritt.
- **Nachtrag vom 02.10.2026, Rechte als Katalog und Rollen als Zeilen.** Punkt 3 sagt, das Fundament führe Rollen als Daten. Gebaut ist es mit `opengewerk-haustechnik#8` so: die Rechte einer Anwendung sind ihr Katalog, eine Liste, aus der sie mit `rightsCatalogue` die Fragen bekommt, die Guard, Abgleich und Oberfläche stellen; die Rollen eines Mandanten sind Zeilen der Tabelle `tenant_roles`, und die Identität einer Anfrage trägt die Rechte, zu denen sich die Rollen ihrer Zugehörigkeit in diesem Moment addieren. Sechs Dinge sind dabei entschieden. **Erstens: die Zeile ist die Wahrheit, auch für die mitgelieferten Rollen.** Ihre Rechte stehen in der Zeile und nicht als Verweis auf den Code. Der Grund ist das Änderungsprotokoll: was eine Rolle darf, ändert sich dann nur durch eine Änderung an einer Zeile, und die steht im Protokoll des Mandanten, auch wenn ein Update sie bringt. Der Preis ist, dass ein neues Recht für eine mitgelieferte Rolle eine Migration braucht, die es in die Zeilen schreibt; ein Test der Anwendung hält die Zeilen eines Mandanten von vor der Migration gegen die Rollen im Code und wird sonst rot. **Zweitens: die Anwendung schreibt die Zeilen, wenn ein Mandant entsteht**, in derselben Transaktion (`writeRoles`), bei der Ersteinrichtung das Fundament aus `AccessRules.shippedRoles`. Kein Trigger: die Rollen blieben sonst in zwei Sprachen stehen, im Code und in einer Funktion der Datenbank. Ein Mandant ohne Zeilen hat niemanden mit einem Recht, ein Fehler fällt also geschlossen aus. Damit ein Update keinen solchen Mandanten hinterlässt, gibt die Anwendung beim Start jedem Mandanten ohne eine einzige Rolle die mitgelieferten (`completeRoles`): zwischen Migration und Start läuft die Fassung davor weiter, und ein Mandant, den sie in diesem Moment anlegt, hätte sonst keine. Ein Mandant, der Rollen hat, bleibt dabei, wie er ist. **Drittens: was sich nicht abschalten lässt, hängt an keinem Recht.** Ob eine Rolle den Mandanten führt und ob sie einen zweiten Faktor verlangt, sind Spalten der Rolle. Die letzte Person, die führt und noch hineinkommt, wird über diese Spalte gezählt, und wer führt, bekommt die zwei Rechte der Verwaltung dazu, was immer die Zeile seiner Rolle sagt. **Viertens: ein Recht, das eine Zeile nennt und der Katalog nicht kennt, gibt nichts**, und ein Schlüssel an einer Zugehörigkeit, zu dem es keine Zeile gibt, ist keine Rolle. So bricht weder eine ältere noch eine neuere Fassung an den Zeilen der anderen. **Fünftens: der Guard fragt die Rechte der Identität selbst.** Ob jemand ein Recht hat, sagt ihm keine Anwendung mehr; sie sagt, was eine Ablehnung in ihren Worten heißt und wer die Instanz betreibt. **Sechstens: die Anwendungsrolle darf die Tabelle lesen und beim Anlegen füllen, mehr nicht**, bis ein Mandant eigene Rollen anlegen kann. Die Tabelle heißt `tenant_roles` und nicht `roles`, weil das Fundament mit "Rollen" an anderer Stelle die der Datenbank meint. Die Oberfläche bekommt die Rechte in einem eigenen Schritt mit der Liste der Mandanten vom Server.
- **Nachtrag vom 02.10.2026, ein Bildschirm fragt, was der Server aufgelöst hat.** Das ist der Schritt, den der Nachtrag darüber ankündigt. `GET /auth/tenants` nennt je Mandant neben den Schlüsseln der Rollen ihre Namen dort, die Rechte, zu denen sie sich addieren, und ob eine von ihnen einen zweiten Faktor verlangt (`TenantChoice` in `platform-domain`). Aufgelöst wird wie bei der Identität einer Anfrage, aus den Zeilen des Mandanten über den Katalog der Anwendung. Weil die Rollen eines Mandanten nur in ihm sichtbar sind, tritt die Route dafür in jeden Mandanten ein, in dem die Person arbeitet; die Zugehörigkeiten, die sie einen Moment davor außerhalb jedes Mandanten gelesen hat, sagen, dass sie das darf. Ein Bildschirm entscheidet nach diesen Rechten, was er anbietet, und hält keine eigene Liste, was eine Rolle darf: er und der Guard können so nicht zu zwei Antworten über eine Rolle kommen, die ein Mandant geändert hat. `GET /staff/roles` nennt, wer einen Mandanten führt, die Rollen, die er hat; danach bietet ein Bildschirm an, was die Routen daneben annehmen. Was ein Gerät für den Start ohne Netz behält, sind seitdem die Rechte. Eine Liste, die die Fassung davor behalten hat, liest die Handwerkersoftware einmal über ihre mitgelieferten Rollen; das ist ihre Sache und nicht die des Fundaments, das keine Rollen im Code kennt, und eine neue Anwendung braucht es nicht. Was ein Bildschirm zeigt, bleibt eine Höflichkeit: entschieden wird jede Anfrage dort, wo sie ankommt.
- **Nachtrag vom 02.10.2026, Tabellen, deren Aufzählung die Liste einer Anwendung ist.** Punkt 3 nennt Nummernkreise und Einstellungen unter dem, was über die Liste der Anwendung kommt; die versiegelten Zugangsdaten gehören aus demselben Grund dazu (`opengewerk-haustechnik#9`, erster Teil). Alle drei sind Tabellen, in denen eine Spalte ein Enum der Datenbank ist: der Zweck eines Geheimnisses, der Schlüssel einer Einstellung und ihre Einheit, der Schlüssel eines Kreises. Welche Werte es hat, weiß nur die Anwendung, und die Handwerkersoftware behält ihre Enums, wie sie sind. Vier Dinge sind dabei entschieden. **Erstens: im Fundament ist eine solche Tabelle eine Funktion** (`secretsSchema`, `tenantParametersSchema`, `numberRangesSchema`), die aus der Liste der Anwendung Tabelle und Enum macht, unter denselben Namen in jeder Anwendung. Eine Spalte mit freiem Text statt des Enums hätte die Liste aus der Datenbank genommen, und eine Zeile könnte dann für einen Kreis zählen, den es nicht gibt. **Zweitens: der Speicher über der Tabelle ist eine Fabrik.** Sie nimmt die Tabelle der Anwendung und das, was nur diese weiß: wie eine Einstellung in einem Satz heißt, in welcher Einheit sie zählt und was ihr Wert sein darf, mit welchem Muster ein Kreis beginnt und in welches Jahr ein Moment fällt, denn die Zeitzone der Mandanten kennt das Fundament nicht. Den Wert einer Einstellung prüft damit der Speicher, bevor er schreibt, in den Worten der Anwendung, und nicht nur die Route, die ihn meistens bringt. Die Anwendung bindet einmal und benutzt, was herauskommt; ein Register gibt es auch hier nicht. **Drittens: was eine solche Tabelle an Rechten und Triggern braucht, beschreibt das Fundament** (`secretsGuard`, `tenantParametersGuard`, `numberRangesGuard`), aber nicht in der Liste seiner eigenen Tabellen, denn dort stünde eine Tabelle, die es ohne die Anwendung nicht gibt. Die Anwendung nennt, welche sie angelegt hat (`MadeByTheApplication`); damit bauen die Ausgangsmigration einer neuen Anwendung und der Baukasten der Tests das Fundament, und der Vergleich am Katalog schließt diese Tabellen in beide Richtungen ein. **Viertens: die Beschreibung sagt, was die Tabelle braucht, und nicht, was eine frühe Migration vergeben hat.** Ein Nummernkreis wird nie gelöscht, denn ein Kreis, der weg ist, begänne wieder bei eins. Die Handwerkersoftware hatte der Anwendungsrolle das Löschen seit Migration 0002 erlaubt, ohne dass etwas es benutzte, und nimmt es mit Migration 0064 zurück, statt dass jede weitere Anwendung das Recht erbt. Die Musterprüfung eines Kreises und das Bauen einer Nummer aus Muster und Zähler stehen in `platform-domain`, wo Formular und Server dieselbe Funktion fragen; ihre Sätze sprechen von einer Nummer und nicht von einem Beleg. Der Schlüssel, mit dem Zugangsdaten versiegelt werden, wird unter denselben Angaben abgeleitet wie bisher, sonst öffnete eine Installation nach dem Update keines ihrer Passwörter mehr; dass darin der Name der Organisation steht und nicht der einer Anwendung, ist deshalb Absicht. Die Tests der drei Speicher laufen im Fundament mit Listen, die niemandem gehören: ein Postfach und ein Schließfach, die Aufbewahrung von Notizen in Nächten, Pakete und Besuche. Der Bereich der Instanz folgt in einem eigenen Schritt.
- **Nachtrag vom 02.10.2026, der Bereich der Instanz.** Das ist der Schritt, den der Nachtrag darüber ankündigt, und `opengewerk-haustechnik#9` ist damit abgeschlossen. Wer die Instanz betreibt, ihre Einstellungen, ihr Protokoll, die Liste der Mandanten, der Weg zu einem weiteren Mandanten und die zwei Befehle der Kommandozeile liegen in `platform-server`, die Tabellen im Einstieg `/schema` und was `drizzle-kit` nicht schreibt im Baustein `instance.sql`. Der Bereich hat keine Liste einer Anwendung; entschieden ist dabei viererlei. **Erstens die Wörter.** Der Nachtrag zur Anmeldung sagt, ein Satz, der einen Mandanten nennt, komme ganz aus der Anwendung. Hier gilt dasselbe für den, der die Instanz betreibt, und es ist nicht nur eine Frage des Geschmacks: was die Handwerkersoftware den Betreiber einer Instanz nennt, nennt die Haustechnik ihre Mandanten. Jeder Satz, der eines von beiden nennt, steht deshalb unter `AccessRules.sentences.instance`, auch was die zwei Befehle auf dem Terminal sagen, und ein Test hält fest, dass im Fundament keines dieser Wörter in einem Satz steht. **Zweitens: wer führt, steht in den Rollen.** Die Liste der Mandanten fragte, wer die Rolle namens `owner` hält. Seit die Rollen Zeilen sind, sagt eine Zeile, ob ihre Rolle führt, und die Liste fragt das (`tenants_with_leads()`): eine Zugehörigkeit oder eine Einladung zählt, wenn eine ihrer Rollen eine Rolle dieses Mandanten ist, die führt. Die Funktion läuft als Eigentümer der Tabellen, also trägt `tenant_roles` dafür die Policy `readable_by_the_owner` wie die Tabellen daneben. **Drittens: zwei Nähte fallen weg.** Wer die Instanz betreibt, sagte dem Guard bisher die Anwendung, und was aus dem ersten Konto einer Instanz wird, ebenfalls. Beides weiß jetzt das Fundament selbst: der Guard fragt den Bereich, und die Ersteinrichtung benennt das erste Konto in ihrer Transaktion. Eine Naht, die jede Anwendung mit demselben Wert füllt, ist keine. **Viertens: der weitere Mandant für einen selbst bleibt eine Route der Anwendung.** Wie ein Mandant entsteht, mit seinen Rollen und mit jemandem, der ihn führt, ist das Fundament (`createOwnTenant`, `createTenantFor`, `createTenantWithLead`). Ob jemand für sich selbst einen anlegen darf und hinter welchem Recht, entscheidet die Anwendung; das Fundament nennt dafür kein Recht, sonst müsste jede Anwendung es führen. Der Bereich war noch in keiner Fassung der Handwerkersoftware erschienen. Ihre Migration 0065 entfernt deshalb `instance_tenants()` im selben Schritt, in dem die neue Funktion kommt, und die Antworten des Bereichs heißen `leads` und `invitedLeads`, ohne dass ein installierter Client die alten Namen erwartet. Aus einer Gegenprobe dabei kommt eine Katalogfrage des Baukastens: jede Funktion, die als ihr Eigentümer läuft, steht mit ihrem Grund auf einer Liste (`readDefinerFunctions`), die des Fundaments dort, die einer Anwendung bei ihr. Der Vergleich der Bausteine lässt einer Anwendung mehr Funktionen, als die Bausteine nennen, und sah deshalb nicht, wenn eine stehen blieb, die gehen sollte. Die Tests des Bereichs laufen im Fundament mit echter Anmeldung, und die Anwendung der Tests nennt, wer ihre Instanz betreibt, mit einem Wort, das keine echte Anwendung hat.
- **Nachtrag vom 02.10.2026, die Oberfläche als Quelltext.** Mit `opengewerk-haustechnik#12` beginnt das dritte Paket. `platform-web` trägt zuerst, was ADR 0004 im Nachtrag vom 19.09.2026 das Designsystem nennt und was bis dahin unter `packages/web/src/styles` und `packages/web/src/components` lag: die Design-Tokens, das Stylesheet eines Einstiegs mit den Schriften und die Bausteine. Abgleich-Client, Sitzung, Tor und Hülle folgen in eigenen Schritten. Vier Dinge sind dabei entschieden. **Erstens: das Paket wird als Quelltext übergeben und hat keinen eigenen Bau.** Seine Einstiege zeigen auf `src`. Punkt 8 sagt, die einbindende Anwendung übersetze die Pakete mit ihrem eigenen Werkzeug; bei einer Oberfläche ist dieses Werkzeug der Bundler, der jede Datei eines Einstiegs ohnehin anfasst, und Tailwind erzeugt eine Klasse nur, wenn es sie im Quelltext liest. Gegengeprüft am selben Tag: Turborepo lässt die Tests der Anwendung neu laufen, sobald sich eine Datei des Pakets ändert, obwohl das Paket keinen Schritt `build` hat. **Zweitens: das Stylesheet nennt sein Paket selbst als Ort, an dem Klassen stehen** (`@source`). Ohne die Zeile fehlt jede Klasse, die nur ein Baustein benutzt, und nichts meldet es: der Bau ist grün, und ein Knopf hat keine Höhe. Gemessen beim Umzug: ohne die Zeile war das Stylesheet der Handwerkersoftware 3.581 Bytes kleiner, mit ihr ist es Byte für Byte das von davor. Ein Test im Paket hält die Zeile fest. **Drittens: was ein Baustein über eine Anwendung wissen müsste, bleibt bei ihr.** Der Status eines Belegs ist nicht mit umgezogen, weil seine Zustände die der Handwerkersoftware sind; im Fundament liegt die Marke, aus der er gebaut ist. Ein Test im Paket hält fest, dass es von keinem Paket einer Anwendung abhängt, dass in ihm kein Produktname steht, auch nicht in einem Kommentar, und dass außerhalb der Kommentare kein Satz und keine Zeichenkette nennt, wie die Handwerkersoftware ihre Mandanten, ihre Rollen, ihren zweiten Einstieg oder ihre Datensätze nennt. **Viertens: eine Prüfung, die jede Anwendung braucht, ist ein Werkzeug.** Ob eine Klasse einen Token nennt, den es gibt, fragt das Paket seine Bausteine und jede Anwendung ihre Bildschirme, mit derselben Funktion aus dem Einstieg `@opengewerk/platform-web/testing`. Ob jede Farbe benutzt wird, kann nur eine Anwendung beantworten, über ihre Bildschirme und die Bausteine zusammen, denn eine Farbe darf an einem Bildschirm stehen und an keinem Baustein. Die Tests der Bausteine, des Kontrasts und der Stufen sind mit umgezogen, mit Beispieltexten, die keiner Anwendung gehören; die CI einer einbindenden Anwendung prüft sie damit selbst.
- **Nachtrag vom 02.10.2026, der Abgleich auf dem Gerät.** Der zweite Schritt von `opengewerk-haustechnik#12`: der Abgleich-Client mit lokaler Ablage, Postausgang, Projektion, Transport und der Leiste über jedem Bildschirm liegt in `platform-web`, unter dem Einstieg `@opengewerk/platform-web/sync`. Fünf Dinge sind dabei entschieden. **Erstens: die Regeln des Abgleichs sind eine Fabrik in `platform-domain`.** `syncRules` macht aus den Richtlinien einer Anwendung, was Server und Gerät fragen: die Entitäten in der Reihenfolge der Liste, die Richtlinie einer Entität, ob ein Feld dem Server gehört, und die Entscheidung über einen Vorgang. Jede Anwendung hat das jetzt, ohne den Test abzuschreiben, und ein Verstoß fällt beim Laden auf statt in einem Keller. **Drittens: die Oberfläche des Fundaments hat einen Einstieg je Bereich**, die Bausteine an der Wurzel, den Abgleich unter `/sync`, das Werkzeug der Tests unter `/testing`. Ein Browser hält seine Datenbanken je Adresse, und jede Anwendung hat ihre; ein anderer Name ließe auf jedem Gerät einer Installation den Postausgang zurück. Die Handwerkersoftware bindet an der alten Stelle: ihr Client startet mit ihren Regeln und dem Namen ihrer Stoppuhr, und die Baustelle hat ihren eigenen Transport, weil nur sie die Werte der Zugänge mit abruft. Die Tests des Clients und der Leiste sind mit umgezogen und laufen mit Richtlinien, die keiner Anwendung gehören, Regale, Notizen, Pakete, Briefe mit Zeilen und Siegel, Besuche und Stempel, aus dem Einstieg `@opengewerk/platform-domain/testing`; bei der Handwerkersoftware bleibt ein Test ihrer Bindung. - **Nachtrag vom 02.10.2026, das Tor vor der Anmeldung.** Der vierte Schritt von `opengewerk-haustechnik#12`, unter dem Einstieg `@opengewerk/platform-web/gate`: alles zwischen dem Öffnen einer Anwendung und ihrem ersten Bildschirm, also der Rahmen, das Anmelden mit Passwort oder Passkey, der zweite Faktor, die Wahl des Mandanten, die Ersteinrichtung, der Einladungslink und der Link zu einem neuen Passwort, dazu das Abmelden und der QR-Code als Baustein. Die Notiz nach dem Scan eines Etiketts liest einen Code, den nur die Handwerkersoftware kennt, und bleibt bei ihr. - **Nachtrag vom 02.10.2026, die Bausteine der Bildschirme.** Der fünfte Schritt von `opengewerk-haustechnik#12`. Woraus eine Anwendung ihre Bildschirme baut, liegt in `platform-web`, mit einem Einstieg je Bereich. Drei Gegenproben haben dabei Tests gezeigt, die nicht scheitern konnten. Und ob eine Liste einem Klick mit gedrückter Taste im Weg steht, lässt sich nicht an dem Link fragen, auf den geklickt wird: React hört an der Wurzel dessen, was es gezeichnet hat, also erst danach. Bei der Handwerkersoftware hält ein Test fest, was jeder Einstieg übergibt, ihre Sätze zu den Einstiegen und den Einstellungen wörtlich und welches Recht welcher Eintrag verlangt. Innen liest die Engine eine Definition mit allen Arten (`Every<T>`), weil sie aus einer Datei kommen und eine fremde Art tragen kann, und gibt sich der Anwendung mit deren Typ. Der Schlüssel einer Definition darf neben Bindestrichen auch Unterstriche tragen, weil die Haustechnik jeden Schlüssel ihrer Pakete so schreibt; ein Punkt bleibt ausgeschlossen, er trennt außerhalb eines Pakets dessen Namen vom Schlüssel. `definitionProblems` liest eine Definition, als könne sie aus einer Datei kommen: ein Abschnitt oder ein Feld, das kein Objekt ist, eine Auswahl ohne Liste, eine Gruppe ohne Felder und ein Grenzwert, der kein Objekt ist, sind Befunde und kein Absturz; die übrigen Funktionen nehmen nur Definitionen, an denen sie nichts gefunden hat. Das Register fragt von einer Definition nur Schlüssel und Fassung (`Versioned`), weil eine Definition über einem allgemeinen `T` sonst keiner bekannten Form zuzuordnen wäre. Die Tests im Fundament füllen einen Rundgang durch ein Lager aus, der an keiner Anlage hängt, auf einen Raum und einen Zähler zeigt und je Regal einen Prüfpunkt fragt, und lesen ihn mit seiner Fassung; eine zweite Probeanwendung zeigt nur Text und Ja oder Nein.
- **Nachtrag vom 04.10.2026, die Einträge einer Liste beim Unterschreiben, und Schlüssel, die jedes Objekt schon hat.** Aus dem Review der Phase 0 der Haustechnik (`opengewerk-haustechnik#31`, #533). `sealProblems` fragte nur die Blöcke, die in den Werten stehen: eine Gruppe über eine Liste, in deren Werten der Block eines Eintrags fehlte, war vollständig, und ein Prüfpunkt dieses Eintrags blieb ohne Antwort, entgegen der Zusage aus dem Nachtrag darüber. **Wer unterschreiben lässt, nennt der Engine die Einträge jeder Liste, wie sie jetzt stehen** (`SealOptions.items`, je Liste die Kennungen in ihrer Reihenfolge), und sie verlangt dann für jeden Eintrag, was die Gruppe braucht, mit oder ohne Block: "Regale, Eintrag 2: Standsicher fehlt." `formRecordProblem` nimmt dieselbe Angabe für ein Formular, das sich als unterschrieben ausgibt. Ohne die Angabe bleibt eine Gruppe so vollständig, wie ihre Blöcke es sind, und ob für jeden Eintrag ein Block da ist, liegt bei der Anwendung; eine Gruppe ohne Pflichtfeld und ohne Prüfpunkt verlangt für einen Eintrag ohne Block nichts. Der Block eines Eintrags, den es nicht mehr gibt, bleibt und wird gefragt wie zuvor. Die Handwerkersoftware nennt die Einträge nicht, ihr Prüfprotokoll bleibt, wie es ist. **Ein Feld oder Abschnitt heißt nie wie etwas, das jedes Objekt schon hat** (`constructor`): die Werte eines Formulars sind ein Objekt, und unter einem solchen Schlüssel antwortet es, bevor jemand etwas eingetragen hat. `definitionProblems` lehnt den Schlüssel ab, und `sealProblems` und `templateValues` lesen nur, was die Werte selbst halten (`Object.hasOwn`), damit auch eine Definition, die niemand geprüft hat, ein leeres Pflichtfeld nicht als ausgefüllt liest.
- **Nachtrag vom 05.10.2026, was eine Anwendung neben einer Zugehörigkeit führt.** Für `opengewerk-haustechnik#84`. Das Fundament kennt eine Zugehörigkeit mit ihren Rollen und sonst nichts. Die Haustechnik führt daneben, in welchen Bereichen eines Betreibers jemand arbeitet, in eigenen Tabellen (ADR 0003 dort), und ihre Tafeln zeichnen Rolle und Bereiche in einem Dialog: mit der Einladung, und beim Bearbeiten mit einem "Speichern". Zwei Anfragen nacheinander wären dafür falsch, denn scheitert die zweite, hat jemand eine Rolle ohne die Bereiche, die dazugehören, oder ist eingeladen und sieht nach dem Beitritt etwas anderes als gewollt. **Die Regeln einer Anwendung (`AccessRules`) nehmen deshalb `additions` (`MembershipAdditions`)**, drei Aufrufe, die das Fundament in seiner eigenen Transaktion macht, jeweils nach seiner Zeile: `invited` mit einer neuen Einladung, `joined` mit der Zugehörigkeit, zu der eine Einladung wird, und `changed` mit einem Wechsel der Rollen. Was der Rumpf dazu sagt, reist unter `additions` und wird ungelesen weitergereicht (`unknown`): seine Form kennt nur die Anwendung, und sie prüft sie. Lehnt die Anwendung ab, mit einer Ausnahme und ihrem Satz, geht alles zurück: die Einladung entsteht nicht, und die, die sie ersetzt hätte, gilt weiter; beim Einlösen entstehen weder Konto noch Zugehörigkeit, und der Link bleibt gut; die Rollen bleiben, wie sie waren. `joined` läuft im Mandanten und als die Person, die beitritt, wie die zwei Zeilen davor, damit das Protokoll des Mandanten ihren Namen trägt. `changed` wird auch ohne Angabe gerufen, weil eine Rolle ändern kann, was sie für die Anwendung bedeutet (bei der Haustechnik: Leitung und Technische Leitung arbeiten in allen Bereichen), und erst, nachdem das Fundament den Wechsel selbst geprüft hat: eine unbekannte Rolle und die letzte Leitung lehnt es ab, ohne zu fragen. **Kein Register und keine Spalte an einer Tabelle des Fundaments**: die Anwendung hält ihre Angaben in eigenen Tabellen, über `(tenant_id, user_id)` an der Zugehörigkeit und über `(tenant_id, invitation_id)` an der Einladung. Die übrigen Wege zu einer Zugehörigkeit, Ersteinrichtung, `add-staff` und ein weiterer Mandant, rufen nichts: dort gilt, was die Anwendung einer neuen Zugehörigkeit von sich aus gibt. Die Tests laufen mit der Probeanwendung, die nichts führt und festhält, dass und als wer sie gefragt wurde (`authentication/additions.test.ts`). Was die Oberfläche unter "Zugänge" dazu zeigt, kommt mit dem nächsten Teil.
- **Nachtrag vom 05.10.2026, die Ansprechpartner.** Für `opengewerk-haustechnik#85`, Modell und Server. Die Haustechnik führt Ansprechpartner an der Liegenschaft (Abschnitt 4.1 ihres Konzepts), und Abschnitt 2.1 nennt sie unter dem, was passt, sobald seine Bezüge getauscht sind. Der Baustein der Handwerkersoftware kannte Kunde, Objekt und Lieferant in jeder Schicht beim Namen: in drei Spalten, in der Regel, im Controller und in zwei Prüfungen des Abgleichs. **Seitdem ist ein Ansprechpartner ein Datensatz des Fundaments, und woran er hängt, sagt die Anwendung.** In `platform-domain` stehen, wer jemand ist und wie man ihn erreicht (`ContactPerson`, `ContactId`), und `contactRules({ parents, parentText, problems })`: die Felder, die einen Elternteil nennen, die zwei Sätze für einen Kontakt an keinem und an mehreren, und was die Anwendung an den Texten sonst beanstandet, ihre Längen zum Beispiel. Daraus entsteht ein Objekt für Formular, Route und Abgleich (`parentProblem`, `parentOf`, `personProblems`), damit alle drei dieselbe Regel gleich lesen. Den Satz für den fehlenden Nachnamen sagt das Fundament selbst, er braucht kein Wort einer Anwendung. In `platform-server` ist die Tabelle eine Fabrik wie Postausgang und Fristen (`contactsSchema({ columns, constraints })`): Name, Funktion, Telefon und E-Mail, die Spalten des Abgleichs und die Trennung der Mandanten sind des Fundaments; die Spalten der Eltern mit ihren Schlüsseln über den Mandanten, der Prüfung, dass es genau einer ist, und ihren Indizes sind der Anwendung, die sie am Katalogvergleich als ihre eigenen nennt. **Es ist die erste Tabelle, die das Fundament beschreibt und die auf Geräte reist** (`contactsGuard` mit `synced: true`): sie wird markiert und nie entfernt, die Anwendungsrolle hat kein DELETE. Die Routen unter `/contacts` registriert `contactParts({ access, rights, routes })` mit drei Rechten der Anwendung: lesen, anlegen, und berichtigen und entfernen. Eine Art von Elternteil kann ein Recht darüber hinaus verlangen (`parentRight`), gefragt für den Elternteil, den ein Kontakt hat, und für den, den eine Änderung ihm gäbe. Und die Anwendung sieht einen Kontakt, bevor er geschrieben wird, in derselben Transaktion (`place`): sie lehnt ab, was auf nichts zeigt, das für die fragende Person da ist, und gibt zurück, was sie aus dem Elternteil ableitet und keine Anfrage setzt, bei der Haustechnik den Bereich. Die Route kürzt jeden Text, speichert einen leer gelassenen als keinen und lehnt ab, was kein Text ist. Für den Abgleich gibt es `contactRecordRules(rules)`, die Regeln über die Felder eines Kontakts für `recordRulesCheck` (der Nachname, die Beanstandungen der Anwendung und ein Kontakt an mehreren Eltern), und `contactWithoutParent(rules)` für einen Kontakt an keinem: ein Konflikt `record_missing` an diesem einen Vorgang, mit jedem Feld, in dem ein Elternteil stehen könnte. `contacts` steht in `foundationPaths`. Das Vokabular des Fundaments nennt die Tabelle und ihre Felder, `role` als "Funktion", und die Eltern sind eigene Felder der Anwendung (`ownFields`). Die drei Pakettests verbieten den Namen `contacts` nicht mehr. Die Tests laufen mit der Probeanwendung: jemand, den man zu einem Regal fragt, oder die Person, an die ein Brief geht, dazu eine Spalte, die der Server aus dem Regal ableitet. **Die Handwerkersoftware bindet** in `packages/domain/src/model/contact.ts` (`tradeContacts`), `database/schema/contacts.ts`, `api/contact-routes.ts`, `database/record-rules.ts` und `database/sync.ts`; ihr eigener Controller ist weg, ihre Tabelle bleibt, wie sie war, und `drizzle-kit generate` meldet keine Änderung. Migration 0069 entzieht der Anwendungsrolle das DELETE auf `contacts`, das 0001 mit allem anderen vergeben hatte und nichts je benutzt hat, wie 0064 bei den Nummernkreisen. Vier Dinge antworten bei ihr anders als vorher. Ein Kontakt ohne Nachnamen wird überall mit "Der Nachname fehlt." abgelehnt, auch vom Abgleich, der einen Namen aus Leerzeichen bis dahin annahm und einen fehlenden der Datenbank überließ; ihre Formulare fragen dieselbe Regel, bevor etwas in den Postausgang geht. Die Route kürzt Texte und lehnt ab, was kein Text ist. Ein Kontakt, den es nicht oder nicht mehr gibt, wird mit einem Satz gemeldet statt mit "Not Found", und eine Kennung, die keine ist, ebenso. Und der Konflikt eines Kontakts ohne Elternteil nennt alle drei Felder statt zwei, der Lieferant fehlte dort seit #296. Die Oberfläche folgt.
- **Nachtrag vom 05.10.2026, die Oberfläche der Ansprechpartner.** Für `opengewerk-haustechnik#85`, dritter Teil. Was beide Einstiege einer Anwendung über einen Ansprechpartner teilen, steht unter dem neuen Einstieg `@opengewerk/platform-web/contacts`: das Formular für einen neuen (`NewContactForm`), wie jemand heißt (`contactName`, `personName`), die Felder und die Werte eines Formulars, die Reihenfolge einer Liste (`contactFields`, `asContact`, `byName`), die Nummer zum Wählen (`dialable`) und die Frage an die Regeln, bevor etwas behalten wird (`contactTextProblem`). Die Karte des Büros ist `ContactsPanel` unter `/office`, die Liste vor Ort `ContactList` unter `/site`, damit jeder Einstieg nur lädt, was er zeichnet; `contactEntity` steht in `platform-domain`, für Server und Oberfläche. **Was die Anwendung dazu sagt, kommt als Eigenschaft**: woran die Ansprechpartner einer Karte hängen (ein Feld mit der Kennung), ihre Regeln (`contactRules`, dieselben wie an Route und Abgleich), ob die Person davor anlegen und ob sie berichtigen darf, und ihre Wörter. Das sind wenige: wie das Feld heißt, das sagt, was jemand dort ist, mit seinem Beispiel, das Wort auf dem Knopf (`ContactWords`), und für die Karte der Satz, warum ohne Verbindung nichts geht, und der Satz unter der Frage vor dem Entfernen (`ContactsPanelWords`). Vorname, Nachname, Telefon und E-Mail heißen in jeder Anwendung gleich und stehen im Fundament, ebenso "Ansprechpartner" selbst. **Zwei Dinge kamen für die zweite Anwendung dazu.** Eine Anwendung, deren Ansprechpartner nur das Büro pflegt, legt einen an seiner Route an und nicht über den Postausgang: sie gibt der Karte, wie (`make`), und die Karte sagt dann vor dem Ausfüllen, dass Anlegen eine Verbindung braucht, und lässt das Formular ohne nicht abschicken. Und die Karte kennt eine zweite Zeichnung (`dense`): was jemand ist und wie man ihn erreicht, in einer Zeile unter dem Namen, wie die Tafel "Liegenschaft" der Haustechnik die Karte in einer schmalen Spalte zeichnet; Nummer und Adresse bleiben darin zum Antippen, und der Stift bleibt. Die Zeichnung der Handwerkersoftware ist geblieben, wie sie war: ihr HTML ist in 26 Zuständen der Karte im Büro und der Karte am Auftrag vor und nach dem Umzug Zeichen für Zeichen gleich, die Werte der Felder eingeschlossen, gemessen mit einem Geschirr, das nicht im Repository liegt. **Die Liste vor Ort berichtigt nichts.** Die Liste der Handwerkersoftware konnte es (`manage`), kein Bildschirm hat es je eingeschaltet, und kein Test hat es geprüft; umgezogen ist, was gezeichnet wird. Die Tests laufen im Fundament mit der Probeanwendung (jemand, den man zu einem Regal fragt, oder die Person, an die ein Brief geht), bei der Handwerkersoftware bleiben die ihrer Bindung: ihre drei Eltern, ihre Rechte, ihre Wörter und die Karte am Auftrag. Die Haustechnik bindet die Karte im vierten Teil an die Liegenschaft.
- **Nachtrag vom 05.10.2026, "Zugänge" mit einer Rolle je Zugang und Dialogen.** Für `opengewerk-haustechnik#84`, fünfter Teil, und der Schritt, den der Nachtrag über das ankündigt, was eine Anwendung neben einer Zugehörigkeit führt. Die Tafeln der Haustechnik zeichnen je Zugang eine Rolle mit einem Satz, wofür sie da ist, daneben die Bereiche, und beides in einem Dialog mit einem "Speichern". Der Bildschirm des Fundaments kreuzt mehrere Rollen in der Zeile an und speichert im selben Moment; für das, was eine Anwendung daneben führt, hat die Zeile keinen Platz, und zwei Dinge, die zusammen entschieden werden, brauchen einen gemeinsamen Knopf. **Das Fundament hat deshalb zwei Bildschirme, und eine Anwendung bindet einen davon**: `StaffScreen` wie bisher und `StaffDialogsScreen` mit einer Rolle je Zugang. Einer mit einem Schalter läge in beiden Bündeln ganz, und die Handwerkersoftware bekäme ein Aussehen, das ihre Tafeln nicht zeichnen. Was beide sagen, liegt in `office/staff-parts.tsx`. **Was die Anwendung neben einer Zugehörigkeit führt, kommt als Eigenschaft herein** (`StaffAdditions`): der Kopf ihrer Spalte, die Zelle je Zugang und je Einladung, die Felder in beiden Dialogen, womit sie beginnen und was unter `additions` hinausgeht. Der Bildschirm kennt die Form nicht und reicht sie weiter, wie es der Server tut. Solange die Anwendung nicht weiß, was sie führt (`known`), öffnet kein Dialog. Wofür eine Rolle da ist, die Sätze unter den Konten und unter Name und E-Mail und die Karten zwischen den Konten und den Einladungen gibt ebenfalls die Anwendung. **"Speichern" schickt, was sich geändert hat, und das Konto zuerst**: Name und E-Mail gehen an `PATCH /staff/:userId/account`, nur die Hälfte, die anders ist; lehnt die Route ab, bleibt die Rolle, wie sie ist, und der Dialog sagt den Satz des Servers. Rolle und `additions` gehen danach in einer Anfrage an `PATCH /staff/:userId`. Eine Zugehörigkeit mit mehreren Rollen, die es im Fundament weiter geben kann, zeigt keine Karte als gewählt und behält alle, bis jemand eine wählt. **Die Geräte einer Person stehen im Dialog ihres Zugangs**; wer die Liste lesen und nicht ändern darf, erreicht sie über einen eigenen Knopf. Neu für beide Einstiege sind `Dialog` (ein kurzes Formular über der Seite: Escape schließt, ein Tippen daneben nicht, und eine Rückfrage darüber nimmt Escape für sich) und `Choice` (eine von wenigen, als Karten mit einem Satz oder in einer Zeile).

## Bestätigung

Die Entscheidung gilt als umgesetzt, wenn

- `packages/platform/domain`, `packages/platform/server` und `packages/platform/web` bestehen und keines davon von einem Anwendungspaket abhängt, was ein Test festhält,
- `opengewerk-haustechnik` in seiner CI gegen einen festen Commit dieser Pakete baut und testet,
- die Handwerkersoftware dabei in jedem Schritt grün geblieben ist, mit allen Prüfungen aus ADR 0009,
- und die `SECURITY.md` der Organisation den Weg einer Korrektur durch beide Anwendungen nennt.

## Vor- und Nachteile der Optionen

### Option 1: Abschrift

- Gut: geringster Aufwand am Anfang, im Hauptrepository keiner.
- Schlecht: jede Änderung zweimal, und nichts meldet, wenn eine fehlt.
- Schlecht: jede Sicherheitskorrektur von Hand in zwei Repositories.

### Option 2: Übernahme mit Herkunftsnachweis

- Gut: schnellster Start, und die unverändert übernommenen Dateien können nicht still abweichen.
- Schlecht: die angepassten Dateien sind ein Fork. Ruht das Hauptrepository, entwickelt sich das Fundament in der Kopie weiter, und die Zusammenführung kostet später mehr als der Umbau jetzt.
- Schlecht: zwei Stellen, an denen ein Fehler im Fundament behoben werden kann.

Diese Option war die Empfehlung für den Fall, dass Phase 2 der Handwerkersoftware parallel weiterläuft. Der Fall ist nicht eingetreten.

### Option 3: Ein Monorepo

- Gut: nichts muss eingebunden werden, eine Korrektur schließt beide.
- Schlecht: der Einwand aus ADR 0001 gilt wörtlich. Anwendungen verschiedener Betreiber hingen an einem Repository, einem Issue-Tracker und einer Versionsnummer.
- Schlecht: das Repository `opengewerk-haustechnik` gibt es bereits, mit eigenem Konzept und eigener Zielgruppe.

### Option 4: Eigene Pakete im Hauptrepository

- Gut: siehe Konsequenzen.
- Schlecht: siehe Konsequenzen.

### Option 5: Ein eigenes Repository für das Fundament

- Gut: die sauberste Trennung, eigene Fassungen.
- Schlecht: Fundament und Fachlichkeit ändern sich zusammen. 103 von 150 Commits mit Code fassten bisher beides an; jeder davon wären zwei Pull Requests in fester Reihenfolge gewesen.

### Einbindung A: Git-Submodul

- Gut: fester Commit, keine Veröffentlichung, kein Konto. Eine Änderung lässt sich vor dem Merge in der Anwendung prüfen.
- Schlecht: die Unbequemlichkeit eines Submoduls, siehe Konsequenzen.

### Einbindung B: Archiv am Release

- Gut: anonym beziehbar, unveränderlich, passt zum vorhandenen Weg mit Prüfsumme und Signatur.
- Schlecht: jede Änderung am Fundament bräuchte eine Veröffentlichung, bevor die Anwendung sie prüfen kann. Ein Tag ist hier eine bewusste Entscheidung und kein Zwischenschritt.

Bleibt die Wahl für den Tag, an dem Dritte das Fundament ohne Git beziehen sollen.

### Einbindung C: Registry

- Gut: der übliche Weg, mit Versionsbereichen und Werkzeugen, die ihn kennen.
- Schlecht: braucht ein Konto und einen Schlüssel, und GitHub Packages verlangt auch für öffentliche Pakete eine Anmeldung, was die Installation aus dem Quelltext und den Bau des Abbilds träfe.
- Schlecht: pnpm hält frisch veröffentlichte Fassungen zurück. Eine Sicherheitskorrektur käme mit Verzögerung an oder bräuchte eine Ausnahme.

### Einbindung D: Git-Abhängigkeit auf ein Unterverzeichnis

- Gut: kein Konto, Commit in der Lockdatei.
- Schlecht: die Pakete des Fundaments verweisen mit `workspace:` aufeinander, und das löst außerhalb eines Arbeitsbereichs nicht auf.
